# Security model

What this relay does and does not protect, stated as claims you can check against the code rather
than as intentions. It covers pairing and routing integrity at the rendezvous layer. The
end-to-end encryption itself lives in `@kangentic/protocol` and the desktop and mobile apps, not
here.

The short version: the relay pairs two connections that present an identical slot id and forwards
bytes between them. The slot id is the only credential it has. It is a high-entropy secret
generated by the client, and everything below is about what that does and does not buy you.

## The question this answers

> Can an unauthenticated third party cause their connection to be paired into a slot intended for
> two specific peers, or disrupt, observe, or deny that pairing?

**Observe: no.** Not the payload, and not the pairing without the slot id.

**Pair in: only by holding the slot id.** There is no way to widen a match, guess cheaply, or
slip into a slot already in use. And holding the slot id is not enough to impersonate a peer,
because the handshake that runs on top of the relay requires key material the relay never sees.

**Disrupt or deny: yes, if you hold the slot id**, and to a limited extent without it. This is
the honest weak spot and it is covered under [Accepted risks](#accepted-risks).

## What the relay guarantees

Each of these is enforced by code and pinned by a test. `test/pairingIntegrity.test.ts` exists
specifically so this section cannot quietly become false.

**Pairing requires an exact match of the entire slot id.** The slot table is a map keyed on the
full slot string (`src/rendezvous.ts`). No prefix, fuzzy, or normalized matching exists anywhere.
The slot is never lowercased, trimmed, or truncated on any path, and the format check is a pure
predicate that returns a boolean rather than a transformed value (`src/guards/slotFormat.ts`) -
uppercase hex is rejected outright rather than folded to match.

**Exactly the first two connections pair, and the decision cannot race.** There is no `await` or
deferred work between reading and mutating the slot entry, so on Node's single thread the
read-modify-write is atomic. Two connections arriving together can never both believe they are the
second arrival.

**A third connection is rejected, never queued.** A slot that already holds a pair rejects further
arrivals with close code 4409 immediately. There is no waiting list, no takeover, and no
promotion when a paired peer later disconnects.

**A connection cannot be misrouted to the wrong peer.** When one half of a pair closes, the slot
is freed at once while the surviving peer's socket is still completing its close handshake, so
another connection holding the same slot id can claim the freed slot during that window. It still
cannot reach the surviving peer: the survivor's frames are dropped rather than forwarded, because
forwarding checks that the partner socket is open. A late close or a late guard trip from a
torn-down pair also cannot tear down a new pair that has since taken the same slot; every teardown
path checks connection identity first.

**Forwarding is byte-for-byte and content-blind.** Frames are handed to the partner socket exactly
as received. Nothing parses, decodes, or branches on message content; only byte length is read,
for the accounting caps. Buffers are per connection, so frames cannot mix between connections, and
`permessage-deflate` is explicitly disabled, which rules out shared-compression-state attacks.
`test/blindness.test.ts` mechanically enforces that `src/**` never imports the protocol package.

**No slot id reaches a log line.** Not raw, not hashed - no logger call site passes one at all,
and a test enforces that. See [Logging and metrics](#logging-and-metrics).

**Nothing security-relevant depends on a browser-enforced check.** There is no `Origin`, `Referer`,
or `User-Agent` check anywhere, deliberately. Those defend against a browser attaching ambient
authority such as cookies to a cross-site request. This relay has no cookie, session, or ambient
credential of any kind: the sole credential is the slot id in the URL, which a browser never
attaches on its own. An allowlist would break the native clients while adding nothing.

## Why slot ids cannot be guessed

The relay's default `SLOT_ID_PATTERN` accepts 32 or 64 lowercase hex characters, which is 128 or
256 bits. The clients generate them from a cryptographically secure random source, freshly per
pairing ceremony, and the pairing token is single-use with a short expiry.

**Entropy is what makes guessing hopeless, not the rate limits.** This is worth stating plainly
because it is easy to assume otherwise. The rate limiters key on the value being limited and a
previously unseen key starts with a full burst, so an attacker trying a different slot id on every
attempt never trips the per-slot limiter at all. Even granting an attacker unlimited source
addresses and removing rate limiting entirely, the search space is so far beyond reach that
throughput, not policy, is the binding constraint. The per-IP limiter and the connection caps are
cost and abuse controls. They are not what stands between an attacker and your slot.

Two consequences follow, and both matter more than tuning any limit:

- **`SLOT_ID_PATTERN` is load-bearing.** The guarantee is a property of the default. An operator
  who narrows it to a short or low-entropy shape makes slots enumerable no matter how tight
  everything else is.
- **Slot secrecy is the client's job.** The relay accepts whatever matches the pattern; it is
  blind by design and cannot verify that a slot was generated well.

The relay also declines to help an attacker confirm a guess. A slot that is occupied and a slot
that fails the cap check are rejected with the same close code and the same reason string, and the
rate-limit rejections do not distinguish which limiter fired.

## Why holding a slot id is not enough to impersonate a peer

This is the part the relay cannot enforce and does not try to, so it is stated as a dependency
rather than a guarantee.

Peers run their own Noise handshake end to end, through the relay, over bytes the relay never
interprets. Winning a slot puts an attacker in the position of a peer on the wire, but the
handshake then requires key material that does not travel through the relay - for first-time
pairing, the desktop's static public key, which reaches the phone out of band by QR code. Without
it the handshake fails before the first message can even be constructed. Impersonating the other
direction requires a static secret key.

So the outcome of an attacker winning a slot is **denial of that pairing, not compromise of it**.

One consequence deserves care from anyone changing this repository: for first-time pairing the
slot id is also the handshake's pre-shared key. It is not a routing label that happens to be
secret, it is key material. Anyone who can read the request URL learns it, which is why no relay
change may log it, cache it, or move it into a path segment where intermediaries record it more
readily. It is also why the disclosure below about TLS termination matters.

## Trusting client IP addresses

Per-IP rate limits and caps are only as good as the address they key on, so the relay is
deliberately conservative about believing forwarding headers.

By default (`TRUST_PROXY=false`) it ignores every forwarding header and uses the raw socket
address, so a self-hoster with no reverse proxy cannot have their caps bypassed by a forged
header. Turning trust on requires naming the proxy's actual address in `TRUSTED_PROXY_CIDRS`; the
relay refuses to start with trust enabled and an empty list, because that would mean trusting
headers from any peer. Even with trust enabled, headers are honored only when the connecting peer
is itself a listed proxy, so connecting directly to the relay's port to bypass the proxy gets you
your real address rather than whatever you claimed.

When headers are trusted, `X-Forwarded-For` is read from the right (nearest hop first, skipping
trusted hops and unparseable entries) rather than the left, because the leftmost entries are
client-supplied and a proxy that appends rather than replaces preserves them. `CF-Connecting-IP`
is trusted only when it parses as an address. Both requirements exist so that a proxy overwriting
the header is defense in depth rather than the only safeguard.

**One deployment requirement follows:** your proxy must append or overwrite the observed peer
address. A proxy that forwards a client-supplied forwarding header verbatim without adding
anything leaves the forged value as the nearest hop, and no relay-side logic can distinguish that
from the truth.

IPv6 addresses are bucketed to a configurable prefix (`IPV6_PREFIX_BITS`, default `/64`) so a
client cannot rotate through its allocation to get a fresh budget per address.

## Logging and metrics

**Logs contain no slot ids and no client IPs.** The relay logs very little, and no logger call
site passes a slot id in any form. `test/logging.test.ts` enforces this, because the property is
only worth documenting if it fails the build when someone adds `{ slot: conn.slot }` to a log
line. `LOG_SLOT_HASHING` and `SLOT_LOG_SALT` configure the salted hash that any future slot
logging would have to go through; nothing calls it today, so both are currently inert and exist to
make adding one a deliberate act with a safe default.

**Metrics carry no slot ids, no IPs, and no per-slot labels** - only process-wide counters and
gauges. They do still reveal operationally useful shape: how many pairings are live and when they
form, and which guard rejected a connection. That is a feedback channel worth denying a stranger,
so `/metrics` and `/metricz` require `METRICS_TOKEN`; with none set they answer 404 rather than
401, so an untokened deployment does not advertise that a gated surface exists. Serving them
openly is available but has to be chosen explicitly with `METRICS_ALLOW_UNAUTHENTICATED`. The
relay deliberately does not try to infer this from the bind address, since a container binds
`0.0.0.0` whether the host publishes to loopback or to the world.

## Admission control

`AdmissionPolicy` (`src/admission.ts`) is the seam a separate, private control plane uses to gate
access to a hosted instance. It sees connection metadata only - never a socket, a frame, or any
payload - so an entitlement gate can decide *whether* a device may connect without being able to
read what flows through. Because this relay is AGPL-3.0-only, that control plane attaches out of
process over `ADMISSION_WEBHOOK_URL` rather than by importing this package.

Two things an operator needs to know:

- **The shipped binary does not construct the webhook policy.** It is a library seam for an
  embedder calling `createRelay({ admissionPolicy })`. Setting `ADMISSION_WEBHOOK_URL` on a stock
  `docker compose up` gates nothing. The open-source relay is free and accountless by design.
- **Deny with HTTP 200 and `{"allow": false}`.** A 4xx is honored as an explicit deny even when
  `ADMISSION_FAIL_OPEN` is true, since that is the gate deciding rather than failing. A 5xx, a
  timeout, or a network error is treated as the control plane being unavailable and follows
  `ADMISSION_FAIL_OPEN`, which defaults to admitting. Set it to false for any deployment where
  admission is an entitlement rather than a convenience.

## Accepted risks

Things this design does not prevent, stated so nobody has to discover them the hard way.

**Anyone holding a slot id can end that session.** A blind byte-forwarder cannot distinguish a
legitimate peer from an attacker who knows the slot, so whoever wins the slot can occupy it or
trip a guard and tear the tunnel down. They cannot read anything or impersonate anyone; they can
stop the pairing from completing. Slot ids are short-lived and single-use for pairing, which
bounds the window, and both clients recover by starting a new ceremony.

**An operator sees connection metadata.** IP addresses of both peers, connection and disconnection
timing, frame sizes and frequency, and which two connections were paired together. This is
inherent to running any relay, not specific to this implementation. Self-hosting removes Kangentic
from that picture entirely.

**On the hosted instance, TLS is terminated at Cloudflare**, which therefore sees the full request
URL including the slot id. Since the pairing slot id is also the handshake's pre-shared key, that
is key material passing through a third party. It does **not** let Cloudflare impersonate a peer -
that still needs the desktop's static public key, which never crosses the relay - but it does mean
the pre-shared key contributes nothing against an observer at that layer. Self-hosting without
Cloudflare removes that party.

**The reconnect slot id is stable for the life of a pairing**, so an operator can correlate one
device's reconnects over time. This is a property of how the clients derive it, noted here because
it is exactly the kind of metadata this section is about.

**Availability is bounded by the connection caps, on a single instance.** A client with many
source addresses can occupy connection capacity and cause legitimate pairings to be refused. The
per-IP cap forces address diversity, the park timeout bounds how long an unpaired connection
holds a slot, and `MAX_UNPAIRED_CONNECTIONS` keeps parking pressure from consuming the whole
budget and starving pairs that would otherwise establish. Tune the `MAX_CONNECTIONS*` family for
your deployment. Because the slot table lives in process memory, two peers must reach the same
instance to pair at all, so this does not scale horizontally without slot-aware routing.

**Rate limit and cap state is per process.** A restart resets every budget, and separate replicas
do not share state.
